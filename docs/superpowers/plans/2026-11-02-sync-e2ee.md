# Sync-Verschlüsselung Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Alle Werte in `kv_store` liegen nur noch als Chiffretext, Geräte gleichen sich weiter ab, und die 226 bestehenden Zeilen werden ohne Datenverlust migriert.

**Architecture:** `js/sync-crypto.js` enthält nur Kryptografie. `js/sync-engine.js` enthält Zustände, Warteschlange, Abgleich und Migration und bekommt Supabase, Speicher und Schlüsselablage übergeben, damit es in Node testbar ist. `js/sync.js` behält Anmeldung und Oberfläche und verdrahtet die Engine. Eine Änderung am Datenbankschema gibt es nicht.

**Tech Stack:** Web Crypto (AES-256-GCM, PBKDF2-SHA256), IndexedDB, Supabase JS, globale Skripte ohne Bundler, `node:test` in `desktop/`.

**Spec:** `docs/superpowers/specs/2026-11-02-sync-e2ee-design.md`

## Global Constraints

- Keine ES-Module und kein Bundler. Neue Dateien sind globale Skripte, Export für Node nur über `if (typeof module !== "undefined") module.exports = {...}`.
- Der neue Client lädt in keinem Zustand Klartext hoch.
- PBKDF2-SHA256, 600.000 Runden, 16 Byte Salt, 12 Byte IV, AES-256-GCM, Passwort mindestens 12 Zeichen.
- Envelope: `{ "__nook_enc": 1, "iv", "ct" }`, AAD `nook-kv:v1:<user_id>:<key>`.
- Keyring-Key: `__nook_sync_keyring__`. Abgleich-Merker: `__nook_sync_last_catchup__`.
- UI-Texte deutsch, keine hartcodierten Farben (Regel aus `CLAUDE.md`).
- `appId`, `productName` und `app://nook` bleiben unverändert.
- Tests laufen mit `cd desktop && npm test`. Echte Supabase-Daten werden in Tests nie berührt.
- Deploy nur über `scripts/deploy.ps1` aus dem Hauptcheckout.

## Review Focus

Die Tests dazu stehen in der jeweils zuständigen Aufgabe.

1. Ein Gerät mit altem Schlüssel, nachdem die Cloud zurückgesetzt und neu eingerichtet wurde: Es darf nichts mit dem alten Schlüssel hochladen (Task 2).
2. Volles `localStorage` beim Übernehmen eines Cloud-Werts: Der Zeitstempel darf nicht vorrücken, sonst geht der Wert still verloren (Task 3).
3. Zwei Konten nacheinander auf einem Gerät: Schlüssel und Abgleich-Merker dürfen sich nicht vermischen (Task 2, Task 3).
4. Backup-Import im gesperrten Zustand: `syncFlushPending()` darf nicht hängen, die Änderungen werden nach dem Entsperren hochgeladen (Task 2).
5. Zwei offene Tabs auf einem Gerät während der Migration: Der zweite Tab darf keinen Klartext überschreiben und nichts doppelt einrichten (Task 4).

### Task 3: Abgleich

**Files:**
- Modify: `js/sync-engine.js`
- Test: `desktop/test/sync-engine-merge.test.js`

**Interfaces:**
- Produces: `engine.catchUp(): {changed: boolean}`, `engine.initialMerge(): {ok: boolean}`, `engine.applyRemoteRow(row): boolean` (für Realtime).

- [ ] **Step 1: Failing tests schreiben:**
  - `neuer Cloud-Wert`: wird entschlüsselt übernommen, `changed` ist wahr.
  - `Echo`: gleicher Zeitstempel wird ignoriert.
  - `lokal neuer`: wird verschlüsselt hochgeladen.
  - `Key fehlt in der Cloud`: Ist der lokale Zeitstempel neuer als der Merker, wird hochgeladen, sonst nicht.
  - `Speicher voll`: Liefert `setRaw` `false`, rückt der Zeitstempel nicht vor, und der nächste `catchUp` versucht es erneut.
  - `Merker pro Konto`: Der Merker von Konto A gilt nicht für Konto B.
  - `kaputte Zeile`: `catchUp` überspringt sie, behält den lokalen Wert, ruft `onNotice("decrypt_failed", key)`.
  - `initialMerge alles oder nichts`: Mit einer kaputten Zeile schreibt es nichts und liefert `ok: false`.
  - `initialMerge`: Cloud gewinnt, rein lokale Keys werden verschlüsselt hochgeladen, rein entfernte übernommen (wie heute).
  - `Klartext nach Migration`: Wird nicht übernommen. Mit lokalem Wert entsteht eine verschlüsselte Zeile mit neuem Zeitstempel. Ohne lokalen Wert bleibt die Zeile und `onNotice("plaintext_row", key)` wird gerufen.
  - `Klartext vor Abschluss`: Bei `migrationDone: false` wird er angenommen.
  - `Realtime`: Zeitstempel wird nach dem Entschlüsseln noch einmal geprüft. Ein neuerer lokaler Schreibvorgang während des Entschlüsselns gewinnt.
- [ ] **Step 2: Laufen lassen.** Erwartet: FAIL.
- [ ] **Step 3: Implementieren.** Der Merker wird erst nach einem vollständig erfolgreichen `catchUp` gesetzt, mit dem Zeitstempel von dessen Beginn.
